Why this exists

The problem

  • MiniMax H3 emits a clip per generation — a 60 s film is many clips.
  • Clips stitched naively show visibly splices, teleports and drift.
  • Each clip must fit the GPU's VRAM — batch size is a real constraint.
  • Prompts must follow the official H3 format or the model misbehaves.

The answer

assistant generates → validator reviews → render one scene
Chained scenes

The chained-scenes workflow

  • Split the story into scenes (12–17, ~12 s each) — each is one render.
  • Export the final frame of each scene → it becomes the chain frame (<Picture 2>) reference of the next scene.
  • Build the prompt with the assistant, check with the validator, render one scene at a time.
  • Physical continuity: one-way trajectory, no teleports, objects persist.

Hardware-aware planning

VRAM-aware batch splitting

  • Set a fixed total (e.g. 60 s).
  • The assistant asks: "What is the max duration your GPU renders in one generation before running out of VRAM?" — this becomes max_clip.
  • The total splits so each scene ≤ max_clip = one VRAM-fitted batch.
60 s ÷ 12 s / batch → 5 × 12 s scenes
GPU that handles only 8 s → same 60 s becomes ~7–8 scenes, each ≤ 8 s.
Authoring discipline

Physical-continuity rules

  • No crossing walls/doors; environment change is covered by fade or a planned cut.
  • No teleport: the new scene opens with the character already in place; motion is observable.
  • One-way trajectory; objects keep position/state (a clock never regresses).
  • Face anchor only when the face is recognizable; a distant silhouette uses the IDENTITY (silhouette) block instead.
  • Voice-over keeps "lips remain closed"; on-screen lines use normal lip movement.
